# Training, model cards and governance

Run `.venv/bin/python -m backend.training`. Runtime startup performs the same seeded training to provide a credential-free working platform. The current application does not load untrusted pickles.

Seed 42 generates 100 parameter groups of boxes, cylinders, cones, spheres and tori using CadQuery/OpenCascade. Features are principal-curvature samples, their variation, face area and edge count. Nonfinite descriptors, wrong feature width or missing classes abort training. Groups 0–79 train; groups 80–99 form the holdout. There are 1,200 training faces and 300 holdout faces in the current generation.

`surface-rf-v1` uses 24 balanced Random Forest trees, maximum depth 3 and all features per split. `surface-et-v2` uses 64 Extra Trees, maximum depth 12. Both achieve 1.0 macro F1 on this limited analytic holdout; held-out log losses differ (approximately 0.11356 vs 0.00995), and composite sample confidence/disagreement behavior differs. These are actual synthetic evaluation results, not evidence of industrial accuracy or calibrated confidence.

Canonical tree-node fields and values are hashed with SHA-256; the structured-field encoding avoids nondeterministic padding bytes. Artifacts are published under `.runtime/models/packages-v2/<manifest-sha256>/`: `trees.json`, `estimator.joblib` and `manifest.json`. The manifest digest identifies its exact canonical JSON bytes, including source/environment provenance and the estimator checksum; the API exposes that digest as `package_id` outside the manifest. Complete files are staged privately, flushed, and renamed into place. Existing identical packages are verified byte-for-byte and reused without writes; missing/modified files fail closed rather than being repaired silently. Concurrent publishers converge on the same complete package. Legacy tree-hash directories are left untouched and are not imported as verified packages. Both canonical-tree and packaged-estimator digests are recorded. Source snapshots, requirements-lock hashes and Git state identify actual code/environment provenance. Do not commit runtime binary packages. The tracked evaluation report provides readable evidence; historical immutable registry run records, arbitrary candidate creation and long-lived promotion history are not yet a complete lifecycle service.

The pure governance function requires macro F1 ≥ 0.85, compatible schema/runtime, approved licensing and a passing security scan. All gates plus authorization are required for eligibility. A regression test verifies that a poor-quality candidate is rejected. Security remains false because image scanning and deployment review are unfinished; passing a dependency audit alone does not clear the release. The promotion route always returns 403 in this local application.

Limitations: analytic synthetic data, uncalibrated probabilities, possible topology/area correlations and weak free-form surface generalization. The OOD Isolation Forest sees perturbed descriptors of five representative solids only. It is a reproducible screening demonstration, not validated production drift detection. Deviations from mean reference descriptors are diagnostic context, not causal model explanations. Production quality metrics need labeled real-world evaluation; they cannot be inferred from request confidence.

## Studio probability inspection

Inference responses include each face’s primary estimator class probabilities and, when comparison is requested, the other estimator’s actual maximum probability as `comparison_confidence`. The legacy `candidate` field identifies the alternate estimator’s class, including when the primary model is itself the candidate. The UI labels both sides from completed-result model IDs and registry stages, not pending toolbar selections. Probabilities are not calibrated accuracy estimates. Class breakdowns count the real returned faces, and confidence distributions group those returned probabilities.

Package immutability is an application policy on the trusted local filesystem, not write-once storage or a signature scheme. External model uploads/deserialization remain unsupported; startup still trains owned baseline estimators in memory. The publisher never repairs an existing corrupt package. Temporary staging cleans up on handled failures; an abrupt process/host termination may leave ignored staging directories. Atomic visibility is tested for concurrent cooperating publishers; power-loss durability, storage quotas, signed publication, append-only training runs and authenticated release history remain separate requirements.

## Completed training journal

Each successful local baseline training execution now appends one run and its complete model manifest snapshots to `registry.sqlite` under `SHAPEOPS_DATA_DIR` (default `.runtime`). Actual start/completion timestamps and a random execution ID distinguish repeated training of identical packages. All model snapshots and the run row commit atomically; duplicate/malformed snapshots roll back the run. Foreign keys prevent orphan snapshots and SQLite triggers reject UPDATE/DELETE on journal tables. API model records expose `run_id`; it is execution metadata outside the immutable package manifest.

`GET /api/registry/runs?limit=20` lists up to 100 recent completed runs with package links. `GET /api/registry/runs/{run_id}` returns preserved manifest snapshots, checking their manifest digests. These are read-only actual local training records; no historical runs are backfilled or production releases fabricated. Current `/api/registry` remains the active in-memory baseline list. Failed training attempts, arbitrary candidate jobs, authenticated approvals, promotion events, pagination beyond the recent window, backups and durable cloud adapters remain future work. SQLite append-only triggers are application policy, not tamper-proof storage: the filesystem/database owner can alter schema. The journal has no automatic destructive retention; define an archival/storage budget before production.


History readers now open SQLite with URI mode=ro plus query_only, use a single read transaction per response, and never create an absent database or parent directory. Writers retain their separate transactional path. Both summary and detail verify the stored canonical manifest digest and model-reference identity; malformed/non-object manifests, embedded package identities, empty runs and more than sixteen models fail closed. Summaries now validate package links before presenting them, rather than trusting reference columns alone. The model scan reads at most seventeen rows to detect an over-limit run; recent history remains capped at one hundred runs. URI paths are escaped so special characters cannot alter SQLite connection options. This is least-privilege connection handling and corruption detection, not protection against an owner who can rewrite both data and hashes.


## Handled baseline initialization failures

The train entry point now records handled initialization exceptions as separate append-only rows in training_failures. Records contain a random attempt ID, actual start/failure timestamps and one category: validation, storage or execution. Exception messages, paths, stack traces and partial model parameters are not stored or returned. Successful completed model runs keep their existing immutable history; failed initialization records do not count as successful runs. A report-writing failure after model publication may coexist with completed model snapshots, because initialization includes report generation. No rollback of already published immutable packages is implied.

GET /api/registry/failures?limit=20 exposes up to one hundred recent records through a typed, read-only SQLite reader. Legacy journals without the table read as empty without migration; normal journal writes create it. Tests inject explicitly labeled failures into temporary stores; no historical failures are backfilled. This captures handled Exception outcomes only: process kills, crashes, interrupted/in-progress attempts and unavailable storage cannot be reliably recorded by this mechanism. When failure persistence also fails, a generic error is logged and the original initialization exception is re-raised. There is no destructive retention; storage/archival budgets remain open. No candidate execution API, promotion authority or cloud durability is added.

## Isolated local candidate job

Run `.venv/bin/python -m backend.candidate_job --output .runtime/candidate-jobs --timeout 120` from the repository root. Each invocation reserves a fresh UUID directory, records running/terminal state in job.json, and launches actual procedural baseline training in a separate process group. The child receives job-local data and report directories, overriding inherited serving paths, with BLAS/OpenMP thread hints of one. Its candidate manifest is validated before success is recorded. The existing content-addressed package publisher and completed/failure journal preserve actual package provenance inside the job. Candidate security gates remain false until separately verified; no serving selection, API mutation or release authorization occurs.

The parent enforces a positive wall budget capped at 180 seconds, kills/waits for the process group on timeout, discards unbounded worker diagnostics and reads at most 64 KiB of candidate result. Timeout/start/execution/result-validation failures produce terminal metadata without raw exception messages. A handled parent interruption kills the child and records interrupted before rethrowing. Killing the parent/host outright may leave running metadata, so it is not a durable distributed scheduler. Job directories are not automatically deleted; archival quotas remain open. This trusted local CLI is not a public arbitrary-parameter training endpoint, a full memory/filesystem/network sandbox or industrial model validation. Both procedural baselines are trained for their shared evaluation, but only the candidate is selected in job metadata.

## Candidate job discovery

GET /api/registry/candidate-jobs?limit=20 lists actual saved isolated jobs newest-first by start timestamp and ID; limit is one to one hundred. GET /api/registry/candidate-jobs/{id} returns one saved job or 404. The root defaults to SHAPEOPS_DATA_DIR/candidate-jobs and can be set through SHAPEOPS_CANDIDATE_JOB_DIR; point the trusted CLI's --output there. Both endpoints are read-only and do not launch, promote, recover or mutate jobs. Missing roots return empty history without creating directories.

CandidateJob validates finite chronological times, exact scope and state/result relationships: running has no finish/result, only success has a candidate, and successful manifests must have the candidate stage. Saved IDs must match their UUID directory. Job metadata must be a regular file opened without following its symlink, and reads stop at 64 KiB plus one byte; FIFO reads use nonblocking open before type rejection. Root/job symlinks are rejected. Directory discovery is capped at one thousand entries (including unrelated entries); exceeding that cap returns 503 and requires explicit archival rather than unbounded scanning or silent incomplete results. A bounded heap retains at most the requested newest models. Corrupt metadata fails closed instead of fabricating a result. Reserved directories without their first atomic job write are skipped.

The saved running state is not proof a process is still alive: parent/host kills can leave it behind, and readers never invent a terminal outcome. These checks do not defend against a filesystem owner racing/replacing ancestor directories or rewriting valid metadata. Authenticated publication, scheduler recovery, archival policy and cloud durability remain separate requirements.
